Опис і нюанси

Кольорові токени — єдине джерело правди для кольору в усьому кіті: жоден компонент не хардкодить власний колір, а лише посилається на змінну на кшталт --primary. Ця вкладка потрібна, щоб звірити, який саме відтінок стоїть за назвою змінної в поточній темі.

Змінні зберігаються як трійка HSL-каналів без обгортки hsl() (наприклад, --primary: 240 5.9% 10%), тому в CSS їх завжди потрібно явно обгортати: hsl(var(--primary)) або з альфа-модифікатором hsl(var(--primary) / 0.5). Редагувати значення в theme.css можна, але це одразу вплине на всі компоненти в обох темах.

Типовий кейс: перевірка контрасту --foreground на --background перед додаванням нового тексту. Другий кейс: підбір м'якшого розділювача через альфа-модифікатор --border / 0.5 замість введення нового кольору.

Опис і нюанси

Кнопки ініціюють дії (відправити форму, підтвердити, відкрити діалог). .btn-primary — для головної дії на екрані (лише одна на екран), .btn-secondary/.btn-outline — для другорядних дій, .btn-ghost — для дій у щільних інтерфейсах (тулбари, картки), .btn-destructive — лише для незворотних/небезпечних операцій (видалення, відкликання доступу).

Не комбінуйте два акцентні кольори (primary + destructive) в одному ряду дій без чіткої ієрархії — користувач має одразу бачити, яка дія головна. .btn-icon обов'язково потребує aria-label, бо не має текстового вмісту для скрінрідерів. Розмірні модифікатори (.btn-sm/.btn-lg) не задають колір — комбінуйте їх із варіантом (.btn-primary тощо).

Типовий кейс: пара кнопок «Підтвердити» (.btn-primary) / «Скасувати» (.btn-ghost) у футері картки чи модального вікна. Другий кейс: кнопка видалення запису в таблиці — .btn-destructive.btn-sm.

Опис і нюанси

.field — обгортка для пари label+control+hint, яка гарантує однакові вертикальні відступи для будь-якого поля форми. Використовуйте .input для тексту/чисел, .textarea для багаторядкового вводу, .checkbox/.radio для бінарного чи одиничного вибору зі списку.

Завжди пов'язуйте <label> з полем через for/id — це не лише доступність, а й збільшення області кліку. .field-hint розташовується під полем і не повинен дублювати те, що вже сказано в label. .checkbox/.radio стилізовані через appearance: none, тому додатковий wrapper для кастомної позначки не потрібен.

Типовий кейс: форма профілю користувача (ім'я, роль через select, короткий опис у textarea). Другий кейс: група з кількох checkbox для мультизначного фільтра над таблицею.

.card — акцентований контейнер із тінню та рамкою для самодостатнього блоку контенту (профіль, товар, налаштування). .panel — менш акцентований контейнер без тіні, для групування вмісту всередині вже акцентованої області.

Не вкладайте .card у .card — це створює подвійну рамку/тінь і зайвий візуальний шум; для вкладеного угруповання використовуйте .panel. .card-footer призначений саме для кнопок дій, не для довільного тексту. .divider — це <hr>, зберігайте цю семантику розділювача, а не border-top на довільному елементі.

Типовий кейс: картка налаштувань із заголовком, описом, вмістом і кнопками «Зберегти»/«Скасувати» у футері. Другий кейс: панель із коротким поясненням під формою, відокремлена divider.

.tabs — патерн для перемикання між кількома панелями контенту в межах одного екрана без переходу на іншу сторінку. Використовуйте, коли вміст логічно розбивається на незалежні секції, які переглядають по черзі, а не одночасно.

Кількість .tab-trigger має точно відповідати кількості .tab-content за порядком — прив'язка через id не потрібна. Клас .is-active виставляється одночасно і на тригері, і на відповідній панелі.

Типовий кейс: ця сама галерея компонентів (14 вкладок). Другий кейс: вкладки «Огляд»/«Активність»/«Налаштування» всередині картки профілю, як у демо нижче.

.table + .table-wrapper — для табличних даних з однаковою структурою рядків (список користувачів, замовлень тощо). .table-wrapper обов'язковий: саме він забезпечує overflow-x: auto, а не сама .table.

.alert — статичне повідомлення, вбудоване в потік сторінки (лишається, поки користувач не піде з екрана чи не закриє його вручну). .toast — тимчасове спливне повідомлення, що з'являється поверх інтерфейсу і зникає автоматично.

Варіанти alert (destructive/success/warning) передають семантику через колір і рамку, але текст усередині (заголовок + опис) має пояснювати ситуацію без опори лише на колір. .toast керується класом .is-visible і JS-таймером — сам по собі CSS не показує/приховує його автоматично.

Типовий кейс: .alert-destructive над формою після невдалої валідації. Другий кейс: toast «Успішно збережено» після відправки форми чи дії користувача.

.select — стилізований нативний <select>, використовуйте його за замовчуванням для коротких списків (до ~10–15 варіантів), оскільки він безкоштовно отримує клавіатурну навігацію, доступність і мобільну поведінку від браузера. .select-search — комбобокс із фільтрацією для довгих списків, де пошук за назвою швидший за прокрутку.

.select-search не є нативним елементом форми — його значення не потрапляє автоматично у FormData, тому для реальної форми потрібен прихований input або власна серіалізація. Список .select-search-list з'являється через :focus-within, тож клік по опції має встановлювати значення в input JS-обробником (як у демо нижче), інакше фокус загубиться.

Типовий кейс: вибір ролі користувача зі списку з 3–5 варіантів — звичайний .select. Другий кейс: вибір країни чи міста зі списку з сотнями варіантів — .select-search із фільтрацією.

.label-text — це не пов'язаний з полем форми напис, а простий текст лише для читання (на відміну від .label з forms.css, який завжди супроводжує конкретний input). .label-field — пара «підпис + значення» для показу параметра та його поточного стану.

Модифікатор --col (підпис над значенням) — типовий вигляд за замовчуванням; --row (підпис і значення в один рядок) — компактніший варіант для щільних списків параметрів. Не використовуйте .label-field замість .field, якщо значення дійсно редагується користувачем — .label-field лише для читання.

.dropzone — зона для перетягування файлів (drag-and-drop) з альтернативним вибором кліком через приховане input[type=file]. Використовуйте її, коли користувач завантажує один або кілька файлів, а не для звичайного вибору значення зі списку.

Компонент керує лише UI-станом (список обраних файлів, видалення рядка) — реальної мережевої логіки завантаження тут немає. Після вибору файлів дропзона генерує подію uikit:files-selected із деталями { files }, яку застосунок має прослухати самостійно, щоб почати справжнє завантаження на сервер. Клас .dropzone--error виставляється вручну застосунком (наприклад, після невдалої валідації типу файлу) — kit.js його не встановлює автоматично.

    Опис і нюанси

    Розширення базових .input/.select новими патернами: .input-search — поле з іконкою пошуку та кнопкою очищення, .input-number — числове поле з кнопками −/+, .input-color — вибір кольору через нативний color picker із текстовим hex-значенням і швидкими пресетами, .textarea-auto — модифікатор .textarea, що росте разом із вмістом, .input-range — повзунок із видимим числовим значенням поруч.

    Усі патерни самостійно ініціалізуються через UIKit.autoInit() за класом-маркером (.input-search/.input-number/.input-color/.textarea-auto/.input-range) — жодних ручних викликів не потрібно, достатньо правильної розмітки. .input-number-btn поважає min/max/step нативного input і тепер має ширину «за вмістом», а не на всю ширину контейнера. .color-swatches — це окремий блок кнопок поруч із .input-color, що встановлюють колір через data-color.

    Типовий кейс: .input-search у шапці таблиці для фільтрації рядків. Другий кейс: .input-color для вибору акцентного кольору теми чи мітки в застосунку налаштувань.

    Опис і нюанси

    .accordion побудований на нативних <details>/<summary> — розгортання/згортання працює без жодного JS. Використовуйте його для FAQ, довгих налаштувань чи будь-якого контенту, який доцільно ховати за замовчуванням, щоб не перевантажувати екран.

    За замовчуванням кожен .accordion-item (це <details>) розгортається незалежно — можна тримати відкритими одразу декілька. Щоб дозволити лише один відкритий елемент за раз, додайте data-accordion і data-single-open на .accordion-контейнер — UIKit.initAccordion() підхопить це автоматично через autoInit().

    Типовий кейс: розділ «Часті запитання» на сторінці підтримки. Другий кейс: групи розширених налаштувань, згорнуті за замовчуванням, щоб не лякати новачків.

    Що таке ui-kit?
    Дизайн-система на чистому CSS без build-кроку та зовнішніх залежностей.
    Чи потрібен build-крок?
    Ні — достатньо підключити CSS/JS файли напряму через <link>/<script>.
    Чи можна тримати кілька пунктів відкритими?
    Так, якщо не додавати data-single-open на контейнер .accordion.
    Опис і нюанси

    Ця вкладка — не компонент, а інструкція: тут зібрано мінімальний набір файлів, які варто скопіювати в інший проєкт, і фрагмент розмітки для підключення. Використовуйте її як чек-лист перед інтеграцією кіту в новий проєкт.

    Найпоширеніша помилка — скопіювати лише components.css, забувши папку components/ (фасад без неї не працює, бо складається з @import), або забувши fonts/Montserrat/, через що theme.css не знайде шрифти за відносним шляхом.

    Типовий кейс: підключення кіту в новий pywebview-застосунок — досить трьох <link> і двох папок. Другий кейс: оновлення вже інтегрованого кіту — досить замінити css/ і fonts/ повністю, не займаючи index.html/gallery.css.

    Що копіювати в інший проєкт

    Ці файли складають перевикористовувану частину дизайн-системи:

    ui-kit/
├── css/
│   ├── theme.css            (токени — тільки :root / [data-theme] і @font-face)
│   ├── layout.css           (flex/grid-утиліти)
│   ├── components.css       (фасад з @import, включно з links.css і accordion.css)
│   └── components/          (уся папка — окремі файли по компонентах)
├── js/
│   └── kit.js               (UIKit — вкладки, toast, dropzone, лоадери, інпути, акордіон)
├── fonts/
│   └── Montserrat/          (уся папка)
├── favicon.svg              (приклад — замініть на власну іконку)
└── assets/
    └── logo.svg              (приклад-заглушка логотипу — замініть на власний)

НЕ копіювати (лише для цієї галереї-демо та інструментів розробки):
├── css/gallery.css
├── css/builder.css
├── js/gallery.js
├── js/builder.js
├── js/google-fonts-list.json
└── index.html

    Як це працює

    Перемикання теми відбувається через атрибут data-theme="dark" на елементі <html>. Без атрибута (або з будь-яким іншим значенням) застосовується світла тема за замовчуванням.

    Усі кольорові токени визначені у theme.css — не редагуйте їх без наміру, оскільки від них залежать усі компоненти.

    kit.js самостійно ініціалізується на DOMContentLoaded — жодних ручних викликів налаштування не потрібно, достатньо підключити файл.

    Складання не потрібне: немає npm, немає CDN, немає build-кроку. Достатньо підключити три файли CSS, один файл JS та локальні шрифти.

    Вкладка «Конструктор» (dev-інструмент, не входить у список вище) для завантаження шрифтів з Google Fonts і експорту .zip потребує локального HTTP-сервера — відкрийте цю галерею командою python3 -m http.server 8000 у корені проєкту, а потім перейдіть на http://localhost:8000 у браузері. При відкритті index.html подвійним кліком (протокол file://) браузер блокує такі мережеві запити.

    Опис і нюанси

    «Конструктор» — це інструмент розробки (dev-tooling), а не компонент кіту: він дозволяє наживо змінювати кольори (окремо для світлої й темної теми), шрифти, типографічну шкалу, відступи, генерувати таблиці й лейаут-співвідношення, а потім експортувати готову кастомізовану копію кіту. Панель угорі (Зберегти/Завантажити/Скинути/Експорт + дві прев'ю-картки) залишається на екрані незалежно від того, яку внутрішню вкладку конструктора ви переглядаєте.

    Кольори світлої й темної теми зберігаються як два повністю незалежні набори значень — редагування одного ніколи не змінює інший (раніше була помилка, через яку зміна кольору в одній темі непомітно «протікала» в іншу; тепер обидва прев'ю миттєво показують справжній, ізольований стан кожної теми). Завантаження шрифтів з Google Fonts і експорт .zip виконують реальні мережеві запити (fetch) — це працює лише при відкритті галереї через локальний HTTP-сервер, а не подвійним кліком по index.html. Запустіть python3 -m http.server 8000 у корені проєкту та відкрийте http://localhost:8000.

    Типовий кейс: підібрати бренд-кольори окремо для світлої й темної теми та шрифт для нового проєкту, згенерувати стартову таблицю й лейаут, натиснути «Експортувати збірку» — і отримати готову папку ui-kit/ із уже «запеченими» значеннями в theme.css, без жодного ручного редагування CSS.
